# freightutils-eval

A reproducible measurement of how often frontier language models get freight reference
questions right on their own, and how often they get them right with the FreightUtils tools.

The questions are the kind a freight practitioner asks and an agent is asked on their behalf:
an ADR Table A value for a UN number, what the ADR 2027 amendments change, the ADR 1.1.3.6
points of a load, a chargeable weight or a loading-metre figure, an HS heading, an AWB prefix
or a UN/LOCODE. Each question has one value as its answer, so the scoring is deterministic: no
model grades another model.

- **Question set v0.2** (current): 300 questions in six families, generated by script from the
  FreightUtils reference data, every expected value checked against the live site, frozen with a
  sha256 (`questions/v0.2/manifest.json`). The whole set is public: nothing is held out.
  `questions/v0` and `questions/v0.1` are kept as history: v0.1 changed the HS family, and v0.2
  replaces one faulty question and accepts listed alternative place names (below).
- **Harness**: Node, no framework, one adapter per provider over its own HTTP API.
- **Results**: one directory per run under `results/` with the scored tables. The current one
  is the [v0.2 full pass](results/2026-10-21-full-pass/) (see "Results" below).

## Conditions

| | The model gets | System prompt |
|---|---|---|
| **A** | the question only | answer from your own knowledge; if you do not know, say UNKNOWN |
| **B** | the question and the FreightUtils tools, as served by the hosted MCP's `tools/list` (names, descriptions and input schemas as served; `get_subscribe_link` left out), at most 5 tool calls | use the tools, answer with the value only |
| C | web search | **not in v0.** `--conditions C` stops with a message; a later version adds it |

In B the tool results go back to the model verbatim: the text content the hosted MCP returned,
errors included. Tool calls go to `https://www.freightutils.com/api/mcp/mcp`.

## The families

| Family | n | One question asks | Answer format | FreightUtils tool (B) |
|---|---:|---|---|---|
| `adr_table_a` | 70 | one Table A field of an ADR 2025 entry: class, classification code, packing group, tunnel restriction code, limited quantity, labels or hazard identification number (10 each) | the value | `adr_lookup` |
| `adr_2027_delta` | 30 | whether the ADR 2027 amendments change a given Table A column for a UN number, and to what (15 changed cells, 15 untouched entries) | the new value or `NO CHANGE` | none: the tools serve ADR 2025, the ADR 2027 change is on the UN page |
| `adr_exemption` | 30 | the 1.1.3.6 points of a load described in words (18), or whether it exceeds 1,000 points (12) | a number, or YES / NO | `adr_exemption_calculator` |
| `freight_arithmetic` | 60 | chargeable weight with the divisor stated (15), CBM (12), loading metres (12), pallet floor positions when double-stacked (9), sea W/M revenue tonnes (12) | a number | the matching calculator |
| `hs_hierarchy` | 50 | structure only: the 4-digit heading of a 6-digit subheading (20), the 2-digit chapter of a subheading (15) and of a heading (15). No wording, and no classification questions (which code fits a product): that is judgement, not reference | digits | `hs_code_lookup` |
| `identifiers` | 60 | AWB prefix to carrier (15), IATA to ICAO (10) and back (5), UN/LOCODE to place (10), container external dimension (10), ULD base dimension (10) | a code, name or number | `airline_lookup`, `unlocode_lookup`, `container_lookup`, `uld_lookup` |

Every question carries: `id`, `family`, `prompt` (plain English, one fact, the answer format
stated), `expected`, `accept` (the scoring rule), `source` (dataset, edition, record, the
publisher, and the citation the site itself gives), `tool` (the FreightUtils tool and the
arguments that answer it, or `null` with a `tool_note`) and `check` (how the live-site lint
reads the value).

How the set was drawn (`generator/generate.mjs --version v0.2`, seed `freightutils-eval-v0`):

- ADR Table A rows are sampled across classes, round-robin. A UN with several rows appears only
  where its packing group picks one row. No usage read existed to weight by, so the sampling is
  uniform within a class. Entries "not subject to ADR" and carriage-prohibited entries are left out.
- The ADR 2027 changed cells are the cells the site serves for single-row entries (classification
  code, labels, hazard identification number, limited quantity, special provisions). The
  untouched entries are ones that no Table A instruction in the amendment documents names.
- The exemption loads use single-row entries of transport categories 1 to 3 whose 1.1.3.6.3
  quantity basis the name settles (litres for liquids, kg for solids). The expected total is
  computed independently (quantity × 50, 3 or 1) and checked against the site's calculator.
- The arithmetic is computed independently by the generator and checked against the site's
  calculators.
- AWB prefixes come from verified airline records (`active_verified`) where exactly one record
  holds the prefix. IATA codes come from verified records whose code no other current record
  uses.
- UN/LOCODEs are ports and airports with a plain place name.
- Container external lengths of the 20 ft types are left out: the served value is under review
  against ISO 668.

### v0.1: what changed from v0

In v0, 37 of the 50 HS questions asked for a heading title, a chapter title or a subheading
description, scored against the wording FreightUtils serves. That wording is the UN Statistics
Division's condensed text ("Metals; n.e.c., cermets and articles thereof"); a model answering
with the WCO nomenclature's legal text ("Other base metals; cermets; articles thereof") was right
and scored wrong. In the first pass every confident-wrong HS answer was of this kind.

v0.1 scores the HS family on structure only: the heading and chapter numbers, as digits. The
wording questions are **dropped**, not kept as an unscored family: an "agreement with the served
wording" figure says nothing about whether a model is right, and keeping them would have spent
money on answers that are never scored. The other five families are byte-identical to v0 (same
seed, same draws). A structure answer is the code's own prefix, so this family is close to a
floor: it checks that a model reads the hierarchy and answers in the format asked, not that it
knows the nomenclature. v0's results stay in `results/2026-10-20-first-pass-v0/`.

### v0.2: what changed from v0.1

Two faults the v0.1 full pass found, both fixed; nothing else changed (the other 299 questions
are byte-identical to v0.1, and no other scoring rule changed).

- **`identifiers-051` is replaced.** In v0.1 it asked for the base length of the RKN ULD, but the
  value FreightUtils serves for RKN (200 cm) is the unit's overall, contoured length; the base is
  the LD3 base, about 156 cm, so the question had two defensible answers. The id is kept so the
  per-question files line up. The new question asks for a ULD's maximum gross weight in kg, drawn
  by the generator's seed from the records whose `maxGrossWeight` has one basis: the
  manufacturer's structural rating (not a carrier's operational limit), no deck split, a primary
  source confirming the figure, and no conflict, divergence or inheritance flagged on the record.
  That pool is AKE and DPE; the draw is **DPE, 1225 kg**, scored as a number within 0.5%. The
  question was meant to use a record whose provenance the site marks verified, but no ULD record
  is verified yet (all 16 are pending independent verification), so the one-basis rule above is
  the bar used.
- **Place names accept a listed alternative.** The `text` rule now accepts, besides the expected
  UN/LOCODE name, (a) either part of a bracketed or comma alternative, so "Torino (Turin)" and
  "Turin, Italy" match Torino, and (b) a name listed for that place in
  [`questions/aliases.json`](questions/aliases.json): a hand-reviewed file of at most 10 entries,
  only for places in the set, each with its source. It has one entry, Turin for Torino (the
  English name, per the GeoNames gazetteer; UN/LOCODE gives English names as "=" reference
  entries, which the FreightUtils parse does not carry). A wrong name is still wrong however it
  is wrapped. The file's sha256 is frozen in the v0.2 manifest.

## The live-site lint and the freeze

`node generator/verify-live.mjs` calls the hosted FreightUtils tools (keyed) and fetches the UN
pages for the ADR 2027 family. It compares every expected value with what the site serves,
strictly: text must match exactly after normalisation, not just be similar. A mismatch is a bug
in the generator, not in the site. At the v0.1 freeze it checked 300 values with zero mismatches
(`QUESTIONS_DIR` picks the set; the default is `questions/v0.2`). At the v0.2 freeze it again
checked 300 values with zero mismatches.
`--annotate` records the site's own citation text in each question's `source.site_citation`.
`node generator/freeze.mjs --version v0.2` writes the manifest. `npm test` fails if any question
file of any frozen version no longer matches its sha256.

## Scoring

Each answer is one of **correct**, **wrong** or **unknown**. Unknown means the model said it
does not know: UNKNOWN, "I don't know", or an empty answer. **Confident wrong** means wrong and
not unknown. Before scoring, the harness strips wrapping (quotes, backticks, bold, a trailing
full stop, an `Answer:` label). If the model wrote several lines, the last line is scored.

| Rule | Normalisation |
|---|---|
| `code` | upper case; spaces, dots, brackets and quotes removed; a leading UN / IATA / ICAO / HIN label dropped |
| `adr_class` | a leading "Class" dropped |
| `packing_group` | "PG" dropped; 1/2/3 read as I/II/III |
| `tunnel` | brackets and spaces removed: `(D/E)` = `D/E` |
| `limited_quantity` | unit words to `L` / `kg`, spaces removed; `0`, none and not permitted are one value |
| `labels` | split on `+`, commas, "and" and spaces, then compared as a set |
| `number_set` | the numbers, compared as a set (special provisions) |
| `yes_no` | YES / NO from the first word |
| `digits` | digits only |
| `numeric` | first number parsed (thousands commas allowed); within the question's tolerance: 0.5% for the arithmetic and dimensions, exact for points and pallet positions |
| `text` | accents, case and punctuation folded, stop words dropped; token-set Jaccard ≥ 0.8 against the expected place name or a listed alternative of it (`questions/aliases.json`), matched on the whole answer or either part of a bracketed or comma alternative (v0.2) |
| `NO CHANGE` | `no change`, `unchanged`, `does not change` and similar count as NO CHANGE; a changed value never does |

The rules are unit-tested in `test/score.test.mjs`.

Per family and overall, the tables report accuracy, unknown rate, confident-wrong rate, mean
tool calls (B), mean latency, tokens and cost.

## Running it

Node 22 or later. No dependencies.

```
npm test                                   # normaliser tests, frozen-set check, key-string lint
node harness/run.mjs --sample 100 --conditions A,B --repeats 1 --run my-run --dry-run
node harness/run.mjs --sample 100 --conditions A,B --repeats 1 --run my-run --cap 80
node harness/run.mjs --models openai,xai --conditions B            # the full 300
```

- `--sample N` is stratified by family (largest remainder, in proportion to family size) and
  deterministic by `--seed`.
- `--dry-run` prints the estimated cost from the question count, the price table and an
  assumed token count per question, then exits.
- `--cap USD` is a hard spend cap. Spend is counted from the usage fields each API returns,
  priced by `harness/models.json`. Before every call the harness holds back the assumed cost
  of one question. At the cap it stops and writes what it has.
- `--skip provider:reason` leaves a provider out and records why (reasons without commas;
  separate several with commas).
- `--assume-from <summary.json>` uses the tokens a smoke run measured (first call and steady
  state, with a 25% margin) for the estimate and the hold-back, instead of the built-in
  assumption. `--spent-before USD` counts earlier spend (probes, smokes) against the cap.
- Providers run one after another, cheapest first by the estimate, and questions one at a
  time. HTTP 429 and 5xx back off 20 s, 60 s, 120 s, then the question is an error; an account
  out of credit or over its spend cap stops that provider and records why.
- Every answer is appended to `results/raw/<run>/rows.jsonl` as it lands. Running the same
  command again resumes; `--max-minutes N` stops cleanly after N minutes and writes the tables
  so far. `harness/salvage.mjs` rebuilds rows from saved raw exchanges for a provider that can
  no longer be asked (latency is not in the raw files, so it is n/a).
- `harness/rescore.mjs` carries an earlier run's answers into a new run under a newer question
  set, with no API calls: each answer is re-scored against the new question, and errors and
  answers to a replaced question are dropped so the new run asks them again. Carried rows are
  marked `carried_from` and their cost does not count against the new run's cap.
  `--dir-name NAME` names the run directory instead of `<date>-<run>`.

Keys are read only from the environment: `OPENAI_API_KEY`, `GOOGLE_API_KEY`, `XAI_API_KEY`,
`ANTHROPIC_API_KEY`, plus `ANTHROPIC_WORKSPACE_ID` when the Anthropic key is not scoped to a
workspace. A provider whose key is absent is skipped. The FreightUtils key comes from
`FREIGHTUTILS_API_KEY` (or `SMOKE_API_KEY`), sent as `X-API-Key` and as a bearer token. Raw
requests and responses go to `results/raw/` (git-ignored), with `Authorization`, `x-api-key`
and `x-goog-api-key` replaced by `[redacted]`. The scored tables go to `results/<date>-<run>/`:
`summary.json`, `per-question.csv`, `manifest.json` (exact model IDs, settings, prices, docs
URLs, prompts, the sampled ids) and `README.md`. `scripts/lint-keys.mjs` fails the build on any
string shaped like a key.

## Models and prices

One flagship per provider: the newest generally available model on the day, read from the
provider's own docs. No preview or experimental IDs. Temperature is 0 wherever the model
accepts it. Prices are in USD per 1M tokens, standard tier, read on 2026-10-20 from each
provider's pricing page:

| Provider | Model | Input | Cached input | Output | Note | Pricing page |
|---|---|---:|---:|---:|---|---|
| OpenAI | `gpt-6-astra` | 10.00 | 1.00 | 50.00 | refuses `temperature`: runs at the provider default | https://developers.openai.com/api/docs/pricing |
| Google | `gemini-4-argon` | 2.00 | 0.10 | 10.00 | to 30 Nov 2026 (then 4.00 / 0.20 / 20.00); implicit caching only | https://ai.google.dev/gemini-api/docs/pricing |
| xAI | `grok-4.7` | 2.00 | (2.00) | 6.00 | prompts under 200k tokens | https://docs.x.ai/docs/models |
| Anthropic | `claude-fable-5-1` | 10.00 | 0.25 | 50.00 | cache writes 12.50 (5-minute); refuses `temperature`: runs at the provider default | https://platform.claude.com/docs/en/about-claude/pricing |

A cached price in brackets means the page gives none, so cached tokens are billed at the input
price. That overestimates the cost.

## Caveats

- **The site is the reference.** The questions are drawn from the FreightUtils data, and the
  expected values are what FreightUtils serves. Condition B gives the model the same source.
  That is a bias, and the reason for the measurement, so read B as "with this reference
  source", not as "the truth". The values come from the publishers each question names; where
  the site might be wrong, the lint cannot tell (it checks the set against the site, not the
  site against the regulation).
- **The prompts are fixed.** Different wording, or a different system prompt, would give
  different numbers.
- **Models change.** A run measures the model IDs in its manifest, on its date.
- **The set is a sample.** 300 questions, one repeat. The family sizes are small, so a
  per-family figure moves a lot on one answer.
- **One question was faulty in v0.1.** `identifiers-051` asked for the RKN ULD's base length,
  but the served value is its overall length; the models' 156 cm was right. v0.2 replaces it (see
  "v0.2: what changed from v0.1"); the v0.1 full pass is kept as it was scored.
- **HS is scored on structure, not wording (v0.1).** See "v0.1: what changed from v0". The v0
  first pass scored HS titles against the served UNSD wording and is kept, marked superseded.
- **ADR 2027 has no tool.** The FreightUtils tools serve ADR 2025. In B, the `adr_2027_delta`
  family has no tool that answers it, so it measures whether the model reads the amendments
  right from what it knows. It stays scored (it is the clearest product signal in the set), and
  every results table gives accuracy both overall and excluding `adr_2027_delta`, side by side.
